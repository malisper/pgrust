3. THE FOUR DATADIRS
-------------------------------------------------------------------------------
  /data/ro-pgrust   sysbench oltp_read_only dataset, served by pgrust
  /data/ro-cpg      the same dataset,        served by C PostgreSQL 18.3
  /data/rw-pgrust   pgbench scale 6849,      served by pgrust
  /data/rw-cpg      the same dataset,        served by C PostgreSQL 18.3

All four were created with the C 18.3 initdb:
    initdb -D <datadir> --no-locale --encoding=UTF8
pgrust has no bootstrap mode of its own (it exits with
"BootstrapModeMain unported: unit backend-bootstrap (initdb runs against C
postgres)"), so the C initdb is the only way to make a datadir for either
engine.  Both engines then run against byte-identical initdb output, which is
also what makes the two arms' datadirs directly comparable.

Owner of all four datadirs: unix user "postgres" (uid 26), mode 0700.
The benchmark database in every one of the four is named  bench .
Authentication: "trust" from 172.31.0.0/16 (appended to each pg_hba.conf).
Port 5432 is reachable only from members of the audit security group.

4. CONFIGURATION APPLIED TO BOTH ENGINES
-------------------------------------------------------------------------------
Every datadir's postgresql.conf ends with exactly this line:

    include_if_exists = '/opt/audit/audit.conf'

so all four clusters read ONE physical file.  The two arms are therefore
identically configured by construction, not by copy-and-compare.  Contents of
/opt/audit/audit.conf:

    shared_buffers = 16GB
    effective_cache_size = 48GB
    work_mem = 64MB
    effective_io_concurrency = 200
    max_parallel_workers = 8
    listen_addresses = '*'
    max_connections = 500
    io_method = sync
    max_stack_depth = 60000
    max_wal_size = 8GB

Everything else is stock initdb output.  autovacuum is ON (default) on all four.

Notes:
  * effective_cache_size = 48GB on a 32 GB box is intentional.  It is
    PlanetScale's published value and it is a planner hint, not an allocation.
    It is applied equally to both arms.
  * max_stack_depth = 60000 (kB) exceeds the default 8 MB stack rlimit and
    PostgreSQL refuses to start if the rlimit is lower.  The launcher raises
    the stack rlimit to 204800 kB before dropping privileges; the same limit is
    published to interactive logins via
    /etc/security/limits.d/99-audit-stack.conf.
  * nofile is 1048576 (set at instance bootstrap, and re-applied by the
    launcher).  This is load-bearing for pgrust, which is a single process with
    one thread per connection: at the AL2023 default of 8192 the server hits fd
    exhaustion during connection setup, panics, and hangs the client.

Verified live on both engines (identical on both):
    autovacuum=on  effective_cache_size=6291456*8kB (48GB)
    effective_io_concurrency=200  io_method=sync  listen_addresses=*
    max_connections=500  max_parallel_workers=8  max_stack_depth=60000kB
    max_wal_size=8192MB  shared_buffers=2097152*8kB (16GB)  work_mem=65536kB
    server_version=18.3

  The two read-only arms have IDENTICAL relpages and identical 100% visibility
  map coverage, so index-only-scan behaviour is comparable between them.

  Why the VACUUM ANALYZE times differ so much (33 s vs 569 s): on the pgrust
  arm, autovacuum finished covering the tables during the load, so the explicit
  VACUUM could skip all-visible pages.  On the C arm, autovacuum was repeatedly
  cancelled by lock conflicts with the CREATE INDEX statements ("canceling
  autovacuum task" x15 in the server log), so the explicit VACUUM did the full
  scan itself.  Both arms end in the same state (100% all-visible, analysed).
  This is a difference in WHEN the vacuum work happened, not in whether it did.

  An explicit VACUUM ANALYZE was run after pgbench -i on BOTH read-write arms.
  pgbench's own vacuum step runs BEFORE the primary keys are built, so it
  leaves pgbench_accounts un-analysed with respect to its index.  Applied
  identically to both arms, so it cannot bias the comparison.  It completes in
  seconds because pgbench's COPY runs in the same transaction that creates the
  table, which lets PostgreSQL mark the pages frozen and all-visible as they
  are written -- the visibility map is already complete when VACUUM starts.

  A read-write SMOKE was later run against both arms (see section 8), so
  pgbench_history in both rw datadirs is no longer empty and some accounts rows
  have been updated.  That is normal pgbench state and does not invalidate the
  datasets.

7. COMPATIBILITY SHIMS REQUIRED TO RUN THESE BINARIES ON AL2023
-------------------------------------------------------------------------------
These were necessary; they are recorded here because an auditor will see them.

(a) libldap.so.2 for the PGDG RPMs.
    PGDG's EL9 build of postgresql18-libs and postgresql18-server links
    libldap.so.2 (openldap 2.6, which is what RHEL 9 ships).  AL2023 ships
    openldap 2.4, whose sonames are libldap-2.4.so.2 / liblber-2.4.so.2 --
    different filenames, so nothing on the box provides libldap.so.2.
    Resolution: libldap.so.2 and liblber.so.2 were extracted from the public
    AlmaLinux 9 package openldap-2.6.8-4.el9.aarch64.rpm and placed in
        /opt/audit/compat-lib
    published to the dynamic linker by
        /etc/ld.so.conf.d/99-audit-el9compat.conf
    AL2023's own openldap 2.4 is untouched and still present; the two coexist
    because their sonames differ.  The four PGDG RPMs were then installed with
    "rpm -ivh --nodeps" after every OTHER dependency had been installed
    normally from the AL2023 repositories.  Verification: "ldd" on every binary
    in /usr/pgsql-18/bin reports no missing objects.
    Cosmetic consequence: "rpm -V postgresql18-server" still reports
    libldap.so.2 as an unsatisfied dependency, because the library is present
    on disk but is not owned by any RPM.  The binaries link and run correctly.
    Nothing else about the PGDG binaries was modified -- they are the official
    PGDG build, GPG-verified.

(b) A share directory for pgrust.
    pgrust resolves its share directory at the compiled-in Debian-style path
    /usr/share/postgresql/18, whereas PGDG installs to /usr/pgsql-18/share.
    /usr/share/postgresql/18 was created as a directory of symlinks to each
    entry of /usr/pgsql-18/share.
    In addition, PGDG configures --with-system-tzdata and therefore ships no
    $SHAREDIR/timezone at all, while pgrust expects one; PostgreSQL timezone
    files are plain TZif, the same format as the system zoneinfo tree, so
        /usr/share/postgresql/18/timezone -> /usr/share/zoneinfo
    Without this, pgrust refuses to start with
    'invalid value for parameter "TimeZone": "UTC"'.

(c) /etc/profile.d/pgsql18.sh puts /usr/pgsql-18/bin on PATH for all users.
    PGDG installs psql/pgbench/pg_isready outside the default PATH; the audit
    kit's run-oltp-rw.sh invokes "pgbench" unqualified and fails without this.

8. ARM SWITCHING
-------------------------------------------------------------------------------
Only ONE server may run at a time: all four datadirs bind port 5432, and the
box has 4 vCPU and 32 GB against a 16 GB shared_buffers setting.

    /opt/audit/switch-arm.sh {ro-pgrust|ro-cpg|rw-pgrust|rw-cpg|stop|status}

  * Requires root; it re-executes itself under "sudo -n" if you do not.
  * It identifies what is running by DATADIR -- it looks for a live
    postmaster.pid under each /data/<arm> -- never by program name.  Both
    engines present as "postgres" in ps output, so a name-based guard would be
    ambiguous.  "status" prints the arm, the pid, and the resolved
    /proc/<pid>/exe so you can see WHICH BINARY is actually serving.
  * Stopping escalates SIGINT (fast) -> 120 s -> SIGQUIT -> 60 s -> SIGKILL,
    then sweeps stale pidfiles and confirms port 5432 is free.
  * Starting raises the stack rlimit (for max_stack_depth) and nofile, drops to
    the postgres user, and waits up to 180 s for pg_isready.
  * Startup stderr goes to /data/logs/<arm>.log; the running server's own log
    goes to <datadir>/log/ (PGDG's postgresql.conf.sample enables the logging
    collector).

Verified working from the client as user <audit-user> over ssh.

      PANIC                 0
      "panicked" (Rust)     0
      backend crashes       0
      out-of-disk failures  0
      autovacuum worker deaths 0

  ro-pgrust : 8 FATAL, 1 ERROR
  ro-cpg    : 3 FATAL, 15 ERROR
  rw-pgrust : 5 FATAL, 0 ERROR
  rw-cpg    : 0 FATAL, 0 ERROR

  Every one of those lines was classified; all are benign:
    * "terminating connection due to administrator command" -- exactly one per
      clean shutdown, emitted as fast shutdown closes a background connection.
      This accounts for all of rw-pgrust's 5 and 6 of ro-pgrust's 8.
    * 'role "root" does not exist' -- an early pg_isready readiness probe that
      ran as root before the launcher was changed to pass -U postgres.  Two on
      ro-pgrust, three on ro-cpg.  Cosmetic; the probe still detected
      readiness correctly.
    * "canceling autovacuum task" / "canceling statement due to user request"
      (autovacuum context) -- autovacuum yielding to a conflicting CREATE INDEX
      or explicit VACUUM.  Normal PostgreSQL behaviour.  15 on ro-cpg, 1 on
      ro-pgrust.
  Autovacuum workers are alive and have run on every table; no worker deaths.

  All four servers are STOPPED at handover.

11. CROSS-NODE SSH KEY FOR THE AUDIT RUNNERS
-------------------------------------------------------------------------------
The audit kit's run-oltp-ro.sh and run-oltp-rw.sh drive the benchmark from the
client and switch server arms by ssh-ing to <audit-user>@<server-private-ip>.  That needs
<audit-user> on the client to be able to reach <audit-user> on the server, so a
DEDICATED ed25519 keypair was generated as <audit-user> ON the client
(~/.ssh/id_ed25519) and its public half appended to <audit-user>'s
authorized_keys ON the server.  It exists only to let the runners switch arms.
No administrative key was copied to either box, and neither box holds AWS
credentials, ~/.aws files, or an instance profile.
