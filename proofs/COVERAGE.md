# Verification coverage — what the proofs, the fuzzers, and the regress suite actually execute

This tree measures, at line granularity over the SHIPPED source under
`crates/`, which lines are exercised by each of three verification
programs:

1. **Kani proof coverage** (`kani`) — the per-commit tier of the
   equivalence-proof suite (`proofs/SUITE.tsv`), re-run with
   `--coverage -Z source-coverage` (Kani RFC-0011 source coverage).
2. **Differential fuzz coverage** (`fuzz`) — the three differential
   cargo-fuzz targets (`float_in_diff`, `float_out_diff`, `geo_diff`)
   replayed over their checked-in corpora with `cargo fuzz coverage`.
3. **Regress suite coverage** (`regress`) — the full PostgreSQL
   `parallel_schedule` (230 files) run once against a server built with
   `-Cinstrument-coverage`.

Artifacts (all generated by `proofs/coverage/merge-coverage.py`):

- `proofs/coverage/summary.json` — machine-readable summary (schema below).
- `proofs/coverage/verification-coverage.tsv` — per-file / per-crate / total rows.
- `proofs/coverage/files/<slug>.json` — per-file line detail for the viewer.

## READ THIS FIRST — what these numbers do and do NOT mean

**A covered line is not a verified line.**

- A line "covered by Kani" means: some proof harness, exploring its
  **fenced** input domain (the bounds recorded in the ledger row —
  e.g. `nd≤2, |weight|≤2, dscale≤6`), can reach that line. Within that
  domain the exploration is exhaustive — but the fence is the whole
  point. Coverage says *reachable under the fence*, not *proved for all
  inputs*, and certainly not *proved correct*: correctness is the
  equivalence assertion of the harness, which is a separate claim from
  which lines got touched on the way.
- A line "covered by fuzz" means: at least one corpus input executed it
  once. The differential oracle checked that execution against verbatim
  C — nothing more.
- A line "covered by regress" means: one fixed corpus (the pg_regress
  schedule) executed it once, and the file-level output matched C's
  expected output. This is the weakest of the three per line — a line
  can be executed and wrong in a way the suite's queries never observe.

The project's own gate-blindness law (2026-07-24) is exactly the failure
mode a percentage invites: a green number read as a stronger claim than
the instrument makes. Do not quote `any%` as "X% of pgrust is verified".
The honest sentence is: "X% of scope SLOC is *executed by at least one
verification instrument*."

Conversely, an uncovered line is not an unverified line **claim-wise**
(a proved function's ledger row still holds over its stated domain even
if a sibling branch is dark) — but the uncovered list is the actionable
map of where no instrument currently reaches.

## Scope

Per `proofs/coverage/coverage-scope.txt`: the adt crates carrying the
bulk of proved ledger rows plus the two fuzz-overlap crates —

    geo, float, numeric, varlena, network, varbit, jsonb
    (all under crates/backend/utils/adt/)

Chosen because (a) they hold most `proved` rows in the function ledger,
(b) the differential fuzz targets land in float + geo, so the scope can
show all three sources overlapping, and (c) a bounded scope was mandated
on a saturated build host. The regress and fuzz captures are whole-tree
(the lcov inputs contain every instrumented crate); only the Kani runs
and the per-file report grid are scope-bounded. `summary.json`'s
`tree_touched` block reports the whole-tree regress/fuzz footprint.

## SLOC rule (the shared denominator)

A line counts as SLOC iff, after stripping `//` and `/* */` comments, it
contains at least one character other than whitespace and `{}()[];,`.
Blank lines, comment-only lines, attribute-free brace/bracket lines do
not count. `#[cfg(test)]`-gated items, `src/tests.rs` files, and
`tests/` dirs are excluded from the denominator entirely (not shipped
logic). This is a **textual** approximation applied identically to
all three sources (their covered-line sets are intersected with it), so
the three percentages are comparable with each other. It is not a
compiler-grade statement count; do not compare these percentages against
numbers produced with a different rule.

Region-to-line mapping caveats:
- Kani reports source **regions** (spans). Every SLOC line intersecting
  a `COVERED` region is counted — a multi-line region marks all its
  lines, which can slightly overcount relative to LLVM's per-line hits.
- LLVM lcov `DA:` lines with execution count > 0 are counted for fuzz
  and regress.

## How to regenerate

Base: worktree of the target sha. Kani 0.67.0, cargo-fuzz 0.13.2 +
nightly-2026-07-17 (with `llvm-tools`), rustc 1.96.0 for the server
build, homebrew postgresql@18 for initdb/psql/pg_regress, regress corpus
from `../pgrust-reference/vendor/postgres-src/src/test/regress`.

### 1. Kani coverage (per family; per-commit tier of SUITE.tsv)

For each family, take each harness's exact flags from `proofs/SUITE.tsv`
and append `--coverage -Z source-coverage`. Harnesses sharing a flag set
can be batched into one invocation (one build, sequential solves):

    cd proofs/<family>
    cargo kani <SUITE flags> --coverage -Z source-coverage \
        --exact --harness <qualified-name> [--harness ...]

Notes:
- `--exact` requires **fully module-qualified** names; several SUITE
  rows store unqualified names (`eq_biteq` for `proofs::eq_biteq`).
  `proofs/coverage/run-kani-coverage.sh` is the one-at-a-time wrapper;
  qualification for macro-generated harnesses needs a source grep.
- Results accumulate under
  `proofs/<family>/target/kani/<target>/kanicov_<ts>/*kaniraw.json`
  (one JSON per harness, region status COVERED/UNCOVERED, absolute
  source paths — shipped-crate attribution is a path filter on
  `<repo>/crates/`).
- jsonb-probe has **no per-commit tier**; its release-gate cmp cells run
  via `proofs/jsonb-probe/run-cmp.sh <cell> <iters> [nested]` with
  `EXTRA="--coverage -Z source-coverage"` (cell/iters table in
  `run-all.sh`).

### 2. Differential fuzz coverage

    cd fuzz
    # corpora: gen_seeds.sh, or the campaign corpora (session-local;
    # not committed — regenerate or copy before running)
    cargo +nightly-2026-07-17 fuzz coverage <target> corpus/<target>
    $NIGHTLY_SYSROOT/lib/rustlib/<host>/bin/llvm-cov export -format=lcov \
        -instr-profile=coverage/<target>/coverage.profdata \
        target/<host>/coverage/<host>/release/<target> > fuzz-<target>.lcov

(Use the **nightly** toolchain's llvm tools on the fuzz profdata and the
1.96 sysroot tools on the server profdata — profraw formats differ.)

### 3. Regress coverage

    RUSTFLAGS="-Cinstrument-coverage" cargo build -p main_main \
        --bin postgres --profile fast-profile
    PGRUST_BIN=target/fast-profile/postgres NO_BUILD=1 NO_SCORE=1 \
      PGINSTALL=/opt/homebrew/opt/postgresql@18/bin \
      PG_REGRESS=/opt/homebrew/lib/postgresql@18/pgxs/src/test/regress/pg_regress \
      REGRESS_SRC=../pgrust-reference/vendor/postgres-src/src/test/regress \
      COV_PROFILE_DIR=/tmp/covprof OUTDIR=/tmp/covregress \
      proofs/coverage/pg-regress-cov.sh
    llvm-profdata merge -sparse /tmp/covprof/server-*.profraw -o regress.profdata
    llvm-cov export -format=lcov -instr-profile=regress.profdata \
        target/fast-profile/postgres > regress.lcov

`pg-regress-cov.sh` is `scripts/pg-regress-fast.sh` with exactly two
deltas: the server teardown is graceful SIGTERM-then-wait (the stock
runner `kill -9`s the postmaster, which discards the entire coverage
profile — profiles flush in an atexit handler), and the server env pins
`LLVM_PROFILE_FILE=$COV_PROFILE_DIR/server-%p.profraw` (pgrust is
thread-per-backend: ONE process, one profile; `%p` guards the
crash-resume segments, which each start a fresh postmaster).

### 4. Merge

    python3 proofs/coverage/merge-coverage.py \
      --kani-glob 'proofs/*/target/kani/*/kanicov_*/*kaniraw.json' \
      --fuzz-lcov fuzz-float_in_diff.lcov --fuzz-lcov fuzz-float_out_diff.lcov \
      --fuzz-lcov fuzz-geo_diff.lcov --regress-lcov regress.lcov

## summary.json schema (contract for the viewer)

```
{
  "generated": ISO8601,
  "head_sha":  sha the numbers were measured at,
  "sloc_rule": prose statement of the denominator rule,
  "sources":   { kani|fuzz|regress: {kind, meaning, ...provenance} },
  "caveat":    the covered≠verified sentence (display it),
  "scope":     [crate dirs, repo-relative],
  "totals":    {sloc, kani, fuzz, regress, any,
                pct: {kani, fuzz, regress, any}},   // scope-wide
  "tree_touched": { fuzz|regress: {files_touched,
                    covered_sloc_in_touched_files,
                    sloc_of_touched_files} },        // whole tree, see below
  "crates": [ {
      name, path, sloc, kani, fuzz, regress, any,
      pct: {kani, fuzz, regress, any},
      files: [ {path, sloc, kani, fuzz, regress, any,
                detail: "files/<slug>.json"} ]
  } ]
}
```

Counts are SLOC-line counts; `any = |kani ∪ fuzz ∪ regress|`. `pct` is
`100*count/sloc` rounded to 2 places. `tree_touched` denominators are
the SLOC **of files the source touched at all** — they are NOT a
whole-tree percentage (untouched files aren't enumerated there).

Per-file detail (`files/<slug>.json`, slug = path with `/` → `__`):

```
{ "path": repo-relative file,
  "sloc":    [ascending 1-based line numbers in the denominator],
  "kani":    [covered subset], "fuzz": [...], "regress": [...] }
```

A line's display class is derived client-side: member of any/all/none of
the three arrays; lines not in `sloc` are non-code (render neutral).

## Known distortions (measured on this capture)

1. **Coverage instrumentation changes Kani solve times, sometimes
   fatally.** `--coverage` injects one cover property per source region,
   which defeats much of the formula slicing win on string-heavy
   harnesses: e.g. `text-slice::proofs::eq_bytea_substr` proves in
   seconds in the plain per-commit tier but did not solve in 560s under
   `--coverage`. 14 of 165 attempted harnesses walled this way (9 of
   text-slice's 14; jsonb's `eq_cmp_obj_obj_1_2` additionally blew the
   6 GiB RSS watchdog at 226s vs a 22s baseline). Full run ledger:
   `proofs/coverage/coverage-runs.log`.
   Harnesses that walled under coverage are listed in
   `coverage-runs.log`; their functions show as UNDER-covered relative
   to what the plain suite actually proves. No verdict changed on any
   harness that did complete (all completed harnesses reported
   VERIFICATION SUCCESSFUL, matching their ledger status).
2. **Stubbed seams count as covered via the stub.** Harnesses run with
   `-Z stubbing` (mcx allocation stubs etc.); lines reached only inside
   stubbed-out callees are attributed to the stub crate, not the real
   seam implementation — the real implementation shows uncovered.
3. **Kani region granularity** (see SLOC rule): multi-line COVERED
   regions mark every intersecting line; expect a small overcount vs
   LLVM lines.
4. **Regress run environment**: measured run scored 218/230 ok (12 files
   red on this host: create_index, select_distinct, subselect, join,
   portals, tidscan, incremental_sort, limit, partition_join,
   partition_prune, partition_aggregate, memoize) vs the CI cluster's
   230/230 — host-load flakes + local env (homebrew PG 18.4 seed
   cluster, no `regress.dylib` for the C-function tests). Red files
   still execute code up to their first divergence, so regress coverage
   here is a slight UNDER-estimate of the CI cluster suite's true footprint.
5. **Fuzz corpora are session artifacts.** The campaign corpora
   (666/106/705 inputs) live in the fuzzing worktree, not in git; a
   regeneration from `gen_seeds.sh` + a fresh campaign will differ.
6. **The instrumented server is slower** (counter increments +
   `fast-profile` codegen). Irrelevant to which lines execute, but do
   not reuse this binary for any perf number.

## Cost of a full-tree run (if wanted)

- Regress + merge: cheap — the capture already IS whole-tree
  (instrumented build ~3 min on 14 cores, schedule run ~8 min, lcov
  export ~1 min). Extending the report grid to every crate is a
  scope-file edit; the only real cost is artifact size (~2,000 files'
  per-file detail JSONs, est. 30-60 MB).
- Fuzz: minutes per target (corpus replay); bounded by corpus size.
- Kani is the expensive axis: the per-commit tier (862 harnesses,
  ~50 families) at coverage-inflated solve times (~3-10x the SUITE
  baselines, plus one family build each) extrapolates to roughly
  8-16 machine-hours serial on this laptop; the calibration tier is
  out of reach (single cells run minutes-to-hours before inflation).
  CI parallelism by family would bring the fast tier to ~1-2 hours.
